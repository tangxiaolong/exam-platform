# 09 · 微信登录与支付真对接

> 对应 Step 4。目标是把「本地 mock 能跑通」变成「真实商户号能收钱、且钱丢了能自己找回来」。
> 代码位置：`common/wechat/`（登录客户端、支付网关、验签、证书、回调解析）、
> `modules/trade/PaymentCompensationJob.java`（补偿任务）。

## 一、为什么要分两层

微信支付的真实性风险几乎都集中在「回调」这一步：回调可能被伪造、可能被重放、
可能属于别的商户、可能干脆不来。这四件事各有独立对策，混在一起写就一定会漏：

| 风险 | 对策 | 落在哪 |
|---|---|---|
| 伪造回调 | RSA-SHA256 验签（平台证书公钥） | `WechatPayVerifier.verify` |
| 重放旧报文 | 时间戳窗口校验（默认 300s） | 同上 |
| 别人的回调打进来 | `appid` / `mchid` 归属校验 | `V3WechatPayNotifyHandler.parse` |
| 回调不来 | 主动查单 + 超时关单补偿任务 | `PaymentCompensationJob` |
| 平台证书轮换 | 未知 serial 立即刷新 + 定时刷新保留旧证书 | `WechatPayCertificateProvider` |

验签和落账刻意分开：验签只依赖微信的密钥与证书，落账只依赖订单库。
这样 mock 与真实两条入口可以复用**同一段落账代码**，不会出现「本地一套、线上一套」。

## 二、微信登录

`app.wechat.mock=true`（默认）→ `WechatAuthClients.Mock`：由 code 派生稳定 openid。
`app.wechat.mock=false` → `WechatAuthClients.Http`：真实调用 `sns/jscode2session`。

真实实现里有两点容易踩：

1. **失败时 HTTP 状态码通常还是 200**，错误在 body 的 `errcode`。只判断状态码会把「code 无效」当成登录成功。
2. 错误要翻成语义化错误码，前端才能给出可操作提示：

| errcode | 平台错误码 | 用户看到 |
|---|---|---|
| 40029 | `AUTH_WECHAT_CODE_INVALID` | 登录凭证已失效，请重新进入小程序 |
| 40163 | `AUTH_WECHAT_CODE_USED` | 登录凭证已被使用，请重新进入小程序 |
| 45011 | `AUTH_WECHAT_RATE_LIMITED` | 登录过于频繁，请稍后重试 |
| 40013 / 40125 | `AUTH_WECHAT_CONFIG_INVALID` | appid/secret 配置不正确（运维项） |

`app.wechat.mock=false` 但没配 appId/secret 时，`WechatAuthClients.Http` 构造即抛异常——**启动失败**，不是运行期才发现。

## 三、支付 v3

### 3.1 下单（JSAPI）

`POST /v3/pay/transactions/jsapi` → `prepay_id`。

**prepay_id 不能直接给小程序**：还要用商户私钥做二次签名，签 `appId\ntimeStamp\nnonceStr\npackage\n`，
得到 `paySign`，连同 `signType=RSA` 一起交给 `wx.requestPayment`。少这一步的表现是「签名错误」，与参数无关。

平台把可用的参数收在 `PaymentCreateResponse.payParams` 里：

```json
{
  "payNo": "PAY2026...",
  "amountFen": 9900,
  "prepayInfo": "wx1234567890",
  "payParams": {
    "appId": "wx...",
    "timeStamp": "1763...",
    "nonceStr": "...",
    "package": "prepay_id=wx...",
    "signType": "RSA",
    "paySign": "..."
  },
  "mockNotifyUrl": null
}
```

`prepay_id` 有效期 2 小时，所以**每次点支付都重新下单**，不复用库里上一份参数——
复用旧参数的表现是「用户点了支付，收银台弹不出来，日志一切正常」。

### 3.2 回调应答（最容易接错的一处）

| 情况 | 应答 |
|---|---|
| 处理成功 | **HTTP 200** + `{"code":"SUCCESS","message":"成功"}` |
| 验签/解密失败 | HTTP 4xx + `{"code":"FAIL","message":"..."}` |
| 业务拒收（金额不符、支付单不存在） | HTTP 5xx + `{"code":"FAIL","message":"..."}` |

返回平台的 `Result<T>` 包装（`{"code":"0","data":...}`）会被微信判为处理失败并持续重试。
mock 模式下仍返回原包装，保持既有接口契约。

### 3.3 平台证书轮换

回调头里的 `Wechatpay-Serial` 指向签名时使用的那张证书。轮换期新旧并存，因此：

- 缓存按 `serial` 索引，**不能只存一张**；
- 命中不到 serial 时**立即拉一次** `/v3/certificates`（轮换窗口内的新回调全靠这条路径）；
- 定时刷新失败**不清缓存**——旧证书在过期前仍有效，清掉等于把所有回调判失败；
- 启动时拉不到证书只记 error 不阻断启动（微信抖动不该让整个平台起不来），首次回调会再触发。

### 3.4 金额以谁为准

回调里的 `amount.total` 是外部输入，只与本地支付单比对：不一致直接拒收并留痕
（`AMOUNT_MISMATCH`）。**不校验金额等于让支付平台决定扣多少钱。**

## 四、补偿：超时关单与主动查单

`PaymentCompensationJob` 默认每 10 分钟一次（`app.wechat.pay.compensation-cron`），逐租户执行：

对「已创建但超过 `unpaid-timeout-minutes`（默认 15）仍未支付」的支付单：

1. **先查单** `GET /v3/pay/transactions/out-trade-no/{no}?mchid=`；
2. 查回 `SUCCESS` → 走与回调完全相同的落账路径（置 PAID、完成订单、发权益、发消息），来源标记 `QUERY`；
3. 查回 `CLOSED/REVOKED/PAYERROR` → 对齐本地状态为已关闭；
4. 仍是 `NOTPAY` → 调用渠道关单 `POST .../close`，再把本地支付单与订单一起关闭。

顺序刻意是「先查单再关单」：反过来会关掉一笔其实已付款的单，随后到达的回调变成
「已关单却收到支付成功」，只能人工退款。这个分支在代码里显式拒收并 `log.error`（`PAY_PAID_AFTER_CLOSED`），
不静默吞掉。

关单失败也要关本地：否则该单会永远停在待支付，每轮补偿都重复处理它。

健康上报走 `JobHealthRecorder`（`payment-compensation`，预期周期 600s），
单笔异常不中断整个租户——一笔脏数据不该让后面的补偿永远轮不到。

## 五、从沙箱到真实商户号的切换

### 5.1 配置

```bash
APP_WECHAT_MOCK=false            # 等价 app.wechat.mock=false
WECHAT_APP_ID=wx...              # 小程序 appid
WECHAT_APP_SECRET=...
WECHAT_PAY_MCH_ID=1900000000
WECHAT_PAY_API_V3_KEY=<32 字节>
WECHAT_PAY_MERCHANT_SERIAL=<商户证书序列号>
WECHAT_PAY_PRIVATE_KEY_PATH=/etc/exam-platform/apiclient_key.pem
WECHAT_PAY_NOTIFY_URL=https://exam.example.com/api/v1/payments/wechat/notify
```

`app.wechat.mock=false` 时以下任一缺失会**启动失败**：`mch-id`、`app-id`、`api-v3-key`、
`merchant-serial-number`、`private-key`/`private-key-path`、`notify-url`。
`notify-url` 不是 `https://` 开头也直接失败——本地一切正常、线上永远收不到通知，是最难查的一类问题。

### 5.2 验收顺序（建议按此顺序做，每一步失败都能立刻定位）

| 步骤 | 怎么验 | 通过标准 |
|---|---|---|
| 1. 登录 | 小程序置 `mockLogin: false`，真机登录 | 拿到 token；同一微信重复登录仍是同一账号（openid 不变） |
| 2. 下单 | 选商品点支付 | 返回 `payParams`，`wx.requestPayment` 能拉起收银台 |
| 3. 回调 | 沙箱/1 分钱真实支付 | 后端日志 `支付已落账 source=NOTIFY_V3`；订单变 `COMPLETED`；权益到账 |
| 4. 应答 | 观察微信端回调记录 | 微信侧显示「处理成功」，不出现持续重试 |
| 5. 幂等 | 同一笔重放通知（微信会自动重试） | 第二次走 `DUPLICATE_*`，权益只发一次 |
| 6. 金额篡改 | 手工构造金额不符的回调 | 返回 `PAY_AMOUNT_MISMATCH`，订单不完成 |
| 7. 回调丢失 | 停掉服务后支付，再启动 | 10 分钟内补偿任务查到 `SUCCESS` 并自动补单 |
| 8. 超时关单 | 下单后不支付，等 15 分钟 | 支付单与订单变 `CLOSED`，微信侧订单已关闭 |
| 9. 证书轮换 | 平台换证书后观察 | 新 serial 的回调能验过（日志出现「平台证书已刷新」） |

## 六、自动化覆盖与真机边界

`WechatPayCryptTest`（12 个用例，不连网、不需要商户号）覆盖：

- 按官方规则自建签名能验过 / 改一个字节就验不过 / 超窗时间戳被拒 / 缺签名头被拒；
- AES-GCM 往返、AAD 篡改导致解密失败；
- v3 回调「验签 → 解密 → 归属校验」全链路字段解出；
- 他商户回调被拒；未签名回调被拒；
- 未知平台证书显式失败、拉证书失败被显式上报。

**只能在真实环境验的部分**：`wx.requestPayment` 能否拉起、微信侧是否显示「处理成功」、
证书轮换的真实时序、1 分钱真实支付。上面的表 5.2 就是这部分的最小执行集。

## 七、多租户与微信账号归属

**结论：一个微信用户在每个租户下各一个账号，跨租户不共享身份。**

### 判据：机构是 org 还是独立租户

| 机构形态 | `/auth/wechat-login` 传的 `tenantCode` | 考生的账号 |
| --- | --- | --- |
| 机构只是平台下的 `exam_org` | 平台的 code | **同一个人**，错题本与进度连续 |
| 机构是独立租户，数据需完全隔离 | 机构自己的 code | **两个独立账号** |

所以「换个入口变成新账号」不是缺陷，而是**由部署方式决定的语义**。要避免它，把机构建成 org 而不是独立租户即可，不需要改代码。

### 为什么默认选隔离

1. **可逆性**：隔离是「加功能」，共享是「改数据」。将来要做统一账号，加一张 userId 关联表即可，既有数据一行不用改；反过来若一开始就共享，事后拆分要写数据脚本并人工裁定每条记录归谁。
2. **资产归属**：机构组织的考试成绩属于该机构，不该因为考生在别处也有账号而被另一家看到。
3. **合规**：跨机构共享考生数据需要考生授权，默认隔离少一层风险。

### 代码里的事实

- `sys_user_identity` 唯一约束是 `(tenant_id, provider, open_id)`——同一 openid 在不同租户各留一条；
- `loginByWechat` 先 `applyTenant(tenantCode)` 再查身份，缺省落平台租户（向后兼容）；
- 多租户插件自动追加 `tenant_id`，忽略名单里只有 `sys_tenant` 一张表。

### 锁住这个语义的测试

`TenantIsolationLoginTest`：同租户重复登录复用同一账号、跨租户是独立账号、两条身份记录各自归属。

### 无法自动解决的代价

同一微信在 A、B 两个独立租户各有账号时，错题本与学习进度不互通。要打通需要产品层的「账号关联」流程——考生主动确认两边是同一人，之后只共享学习记录，不共享考试与成绩。

## 八、已知限制

1. 回调 IP 白名单未做（当前只依赖验签 + 归属校验；如需再加一层网络 ACL，应在 Nginx 侧配置）；
2. 退款走的是本地 mock/`RefundService` 链路，真实 v3 退款接口（`/v3/refund/domestic/refunds`）尚未接入；
3. 补偿任务只处理「创建后超时未支付」，不处理「已支付但权益发放失败」——后者由对账任务
   （`ReconciliationJob`）以「已支付但无权益」异常的形式检出并进入待处置池；
4. 平台证书只缓存到进程内存，多实例各自维护一份（这是有意的：证书是幂等的公共数据，
   共享缓存带来的复杂度远大于它省下的几次 HTTP 请求）。
