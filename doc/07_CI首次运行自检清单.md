# CI 首次运行自检清单

> 对应工作流：[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)
> 场景：四个 Job 已在本地按等价条件预跑通过，下一步是它们在 GitHub Actions 上的第一次真跑

## 1. 这份清单解决什么

四个 Job 里有两个（`mysql-migration` / `admin-web-build`）历史上从未被真正执行过，另外两个（`backend-test` 的 Redis 段、`api-contract`）也一直是「本机能跑、没人跑」。首次上 CI 出现红是正常的，但要能**区分「环境首次暴露」和「真有缺陷」**——否则很容易把真问题当噪声忽略，或者反过来去「修」本来正确的配置。

这份清单的作用是：给出每个 Job 的**预期数字**，任何偏离都能立刻定位到具体环节。数字以本地预跑实测为准（见第 6 节），不是估算。

## 2. 已在本地消除的必然红点

这些不是「首次跑的预期红」，是**任何环境都必然失败**的真缺陷，均已修复。

### 2.1 历史修复（接入 workflow 之前）

| 问题 | 后果 | 修复 |
| --- | --- | --- |
| `tools/check-api-contract.ps1` 把仓库根写死为 `d:\workspace\teamGitCode` | CI 在 `ubuntu-latest` 上跑它，`Get-ChildItem` 找不到路径 → `api-contract` Job 必红 | 改为从 `$PSScriptRoot` 推导根目录，用 `[System.IO.Path]::Combine` 拼接（跨平台），缺失路径 fail-fast |
| 三个 `.ps1` 含中文注释但保存为无 BOM 的 UTF-8 | Windows PowerShell 5.1 按 GBK 解码 → 乱码打乱引号配对 → 报 `Missing closing '}'`，脚本无法解析 | 统一转为 **UTF-8 with BOM**；`pwsh` 7 与 5.1 均能正确读取 |

### 2.2 首次预跑发现的修复（本次）

本地按 CI 等价条件预跑（Redis 6380 容器 + MySQL 8 容器 + `npm ci`）后暴露出 5 处缺陷，**全部是「平时被跳过 / 从未执行」掩盖的**：

| 位置 | 缺陷 | 后果 |
| --- | --- | --- |
| `RedisRateLimiterIntegrationTest.bucketKeyShouldCarryTtl` | 用 `limiter("it:ttl:")` 构造限流器（内部会再追加随机串），却断言固定 key `it:ttl:user:1` 的 TTL | 断言对象与真实 key 永不是同一个，`getExpire` 恒为 `null` → 用例一直红 |
| `RedisRateLimiterIntegrationTest.twoInstancesShouldShareQuota` | 两个「实例」各自传入前缀、各自被追加不同随机串，落在不同 key 上 | 测的是「互不干扰」而非「共享」：容量 10 时放行 12 → 一直红 |
| `MySqlMigrationSmokeTest` | 断言表名写成 `attempt`，实际迁移出来的是 `exam_attempt` | 迁移本身没问题，断言写错 → 一直红（该用例默认 assumed-skip，所以从未有人看到） |
| `tools/check-mysql-migration.ps1` | 参数用「反引号 + LF」续行，而脚本是纯 LF 行尾 | Windows PowerShell 5.1 不认这种续行，`docker run` 只收到 `run` → 报「参数不足」，演练脚本从未成功执行过 |
| `tools/check-mysql-migration.ps1`、`tools/load-baseline.ps1` | `$ErrorActionPreference='Stop'` 下执行 `docker logs`（stderr 有内容）；以及把含 `&` 的 JDBC URL 直接交给 `mvn.cmd` | 前者被当成终止性错误（永远等不到 MySQL 就绪），后者被 cmd 当成命令分隔符（报 `'allowPublicKeyRetrieval' 不是内部或外部命令`） |
| `tools/check-api-contract.sh` | `while` 循环的输出直接打到 stdout，后续步骤读的是一个刚被 `: >` 清空的文件 | `backend mappings: 0`，于是每条前端路径都报 UNMATCHED——这个 bash 版此前从未被真正执行过（README 一直说 CI 跑 `.ps1` 版） |
| `tools/check-api-contract.ps1` | 正则写在双引号字符串里，字符类中的反引号被解析掉，只匹配单/双引号 | **68 条前端声明里漏扫 42 条**（全是 `` url: `/x/${id}` `` 这种模板字符串写法），`unmatched: 0` 是「没检查」而非「检查过」 |
| 两个契约脚本的归一化 | 只把 `${...}` 与 `{\d+}` 归成 `{id}`，后端路径里的 `{attemptId}` 原样保留 | 前端 `/attempts/{id}/resume` vs 后端 `/attempts/{attemptId}/resume` 永远不相等；且 `${x}` 会被替换成 `${p}`（留下 `$`） |

修复方式：Redis 两条用例改为由测试自己持有完整前缀；MySQL 断言表名改为 `exam_attempt`；PowerShell 脚本改为参数数组 splat + `Invoke-Docker` 包装（放宽 `ErrorActionPreference`、按退出码判成败）+ 用 `cmd /c` 承载带 `&` 的 URL。

## 3. 四个 Job 的预期结果

### 3.1 `backend-test`

- 预期：`Tests run: 159, Failures: 0, Errors: 0, Skipped: 3`
- `Skipped: 3` = `MySqlMigrationSmokeTest`（1，未传 `-Dmysql.test.url`）+ `LoadBaselineTest`（2，压测默认不跑）。这是常态，不是异常。
- **Redis 5 条用例必须是 `skipped="0"`**：Job 里有一段断言专查这一条。若报了 red，说明 `redis:7-alpine` service 没就绪或 `APP_TEST_REDIS_*` 没生效——先看 service 的健康检查（`--health-cmd "redis-cli ping"`），不要先去改测试。
- 若 `Tests run` 总数不是 159：说明有测试类没被编译/被排除，先看 Maven 输出里的 `Running` 清单。
- 若某个业务断言红：本地 `mvn test` 复现（本地已全绿），CI 红则优先查时区、文件编码、路径分隔符。

### 3.2 `api-contract`

两个 bash 静态脚本，都不依赖 Node / JDK / pwsh：

- `check-api-contract.sh`：预期 `backend mappings: 120`、`admin-web calls: 68, matched: 68, unmatched: 0`、`miniprogram calls: 22, matched: 22, unmatched: 0`，退出码 0。PowerShell 版输出同样的数字（两版必须一致，否则说明其中一版漏扫了）。
- `check-frontend-consistency.sh`：预期 `api 对象: 16 个`、`后端 DTO record: 50 个`、`视图: 16 个，路由条目: 15 个`、`FRONTEND CONSISTENCY OK`，退出码 0。

`unmatched` 非 0 → 前端声明的路径在后端不存在，改前端或补接口，这是真缺陷（不是环境问题）。

### 3.3 `mysql-migration`

- 预期：`MySqlMigrationSmokeTest` 1 个用例通过，`tests="1" skipped="0"`。
- 本地已用 Docker + `mysql:8.0` 完整跑通（V1..V10，42 张表、含 V10 对账索引），并断言「重复 migrate 执行 0 个脚本」。
- 排查顺序：
  1. **Skipped 而不是通过** → `-Dmysql.test.url` 没传进去（系统属性名写错、或被 shell 的 `&` 截断）；
  2. **连接失败** → service 未就绪。MySQL 8 首次初始化要 20~40 秒，`health-retries: 15` × 10s 一般够；仍失败就把 `--health-retries` 提到 20；
  3. **迁移脚本报错** → 这才是本 Job 存在的意义：某条 DDL 在真 MySQL 上不成立（索引长度、字符集、`ALTER` 回填）。按 [`doc/05_数据库迁移演练与回滚预案.md`](05_数据库迁移演练与回滚预案.md) 第 4 节规范修脚本（**已发布的脚本只读，修正一律新建版本**）；
  4. **断言「重复 migrate 执行 0 个」失败** → 有脚本未记录成功状态，查 `flyway_schema_history`。
- 本地复现（需 Docker）：`bash tools/check-mysql-migration.sh` 或 `powershell -File tools/check-mysql-migration.ps1`。

### 3.4 `admin-web-build`

- 预期：`vue-tsc --noEmit && vite build` 通过（本地实测通过，含 `index-*.js` 约 1.28 MB 的 chunk 体积警告，属提示不阻断）。
- 依赖已锁定：`admin-web/package-lock.json` 已提交，Job 用 `npm ci` 并按该文件缓存，不再每次解析最新 minor 版本。
- 若红在类型上：`tsconfig.json` 的 `noUnusedLocals` 为 `false`，所以不会因未使用变量报错；`strict: true` 下常见来源是「给组件 prop 传了过宽的类型」「隐式 `any`」「可选 prop 未处理 `undefined`」。
- 本地复现：`cd admin-web && npm ci && npm run build`。
- Windows 本地注意：Node 26 自带的 npm 11 默认不执行包的 install script，`npm ci` 可能先因 `esbuild.exe` 被占用报 `EPERM`。删掉 `node_modules` 重试即可，CI 用的是 Node 20 + npm 10，不受影响。

## 4. 首次「红」的判断流程

| 现象 | 归类 | 处理 |
| --- | --- | --- |
| Job 在 checkout / 环境准备阶段失败 | 环境 | 修 workflow（runner 镜像、CLI 缺失、service 就绪） |
| 只有 `mysql-migration` / `admin-web-build` 红 | 首次暴露 | 按 3.3 / 3.4 排查，属本次引入的门禁价值所在 |
| `backend-test` 红了但业务断言都通过、只有 Redis 段红 | 环境 | Redis service 未就绪或端口没对上，不是代码问题 |
| `backend-test` 红且指向某业务断言 | 真缺陷 | 本地 `mvn test` 复现，优先查时区、编码、路径分隔符 |
| `api-contract` 红且报 `unmatched` | 真缺陷 | 前端声明的路径在后端不存在，改前端或补接口 |
| `api-contract` 报「缺少自检所需路径」 | 环境 | 脚本根目录推导异常，检查 checkout 是否完整 |

## 5. 跑绿后要固化的事

1. 在分支保护里把 `backend-test` 与 `api-contract` 设为 required check，`mysql-migration` 与 `admin-web-build` 至少对 `main` 阻断；
2. 把本文件的实测数字换成 CI 上的实际数字（若有差异，先弄清差异来源再改）；
3. 依赖升级后重跑一次，确认 `npm ci` 仍与 lockfile 一致。

## 7. 已知盲区

| 盲区 | 为什么不覆盖 | 何时补 |
| --- | --- | --- |
| UTC 时区下的行为 | workflow 显式设 `TZ=Asia/Shanghai`，与生产口径一致，避免首次跑被环境差异掩盖真问题 | 若将来要支持多时区部署，加一条 `TZ=UTC` 的 matrix，暴露「代码里假设了本地时区」的地方 |
| 真实微信登录 / 支付回调 | 需要商户号与平台证书，CI 无法提供 | 沙箱环境就绪后单独加 job（`workflow_dispatch` 触发，避免每 PR 消耗配额） |
| 小程序端渲染与真机离线 | 需要微信开发者工具，无法在 headless runner 上跑 | 由 [`doc/08`](08_小程序离线答题与断网重连验证清单.md) 的人工清单承担 |
| 性能压测 | 数字依赖机器，同机同参数才有可比性 | 见 `doc/06`；`LoadBaselineTest` 默认跳过，发版前在预发环境手动跑 |

## 8. 执行侧待办

1. 提交 workflow 与脚本修复后 push，触发首次运行；
2. 按第 4 节判断每个红灯的归类；
3. 跑绿后按第 5 节固化（分支保护 + 数字校准）；
4. 把首次运行的 URL / 耗时记录到本文件末尾，便于后续判断「变慢」是渐进还是突变。
