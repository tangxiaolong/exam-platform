# CI 首次运行自检清单

> 对应工作流：[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)
> 场景：四个 Job 首次在 GitHub Actions 上真跑之前 / 之后

## 1. 这份清单解决什么

本机没有 Node、Docker 与 git 仓库，四个 Job 里有两个只能到 CI 才算第一次真正执行。首次跑出现红是正常的，但要能**区分「环境首次暴露」和「真有缺陷」**——否则很容易把真问题当成噪声忽略掉，或者反而去「修」本来正确的配置。

## 2. 已在本地消除的两个必然红点

这两个不是「首次跑的预期红」，是**任何环境都必然失败**的真缺陷，已修：

| 问题 | 后果 | 修复 |
| --- | --- | --- |
| `tools/check-api-contract.ps1` 把仓库根写死为 `d:\workspace\teamGitCode` | CI 在 `ubuntu-latest` 上跑它，`Get-ChildItem` 找不到路径 → `api-contract` Job 必红 | 改为从 `$PSScriptRoot` 推导根目录，并用 `[System.IO.Path]::Combine` 拼接（跨平台），同时对缺失路径 fail-fast |
| 三个 `.ps1`（契约校验、迁移演练、压测）含中文注释但保存为无 BOM 的 UTF-8 | Windows PowerShell 5.1 按 GBK 解码 → 乱码字符打乱引号配对 → 报 `Missing closing '}'`，脚本根本无法解析 | 统一转成 **UTF-8 with BOM**；PowerShell 7（CI 用的 `pwsh`）与 5.1 均能正确读取 |

验收：契约校验在「仓库根目录」与「任意其他目录」两种调用方式下都通过（`backend mappings: 107 / admin-web 24 matched / miniprogram 12 matched / exit=0`）。

## 3. 四个 Job 的预期结果

### 3.1 `backend-test`（已本地验证）

- 预期：`Tests run: 128, Failures: 0, Errors: 0, Skipped: 2`
- 本地跑是 `Skipped: 8`（含 4 个 Redis 用例、1 个 MySQL 迁移、2 个压测、1 个环境相关）。CI 起了 Redis service，**Skipped 应降到 2**（剩下的是 MySQL 迁移与压测两个按设计默认跳过的类）。
- 若 Skipped 仍是 8：说明 Redis 没连上，`APP_TEST_REDIS_HOST/PORT/DB` 没生效 → 检查 service 容器是否先于测试就绪（`--health-cmd redis-cli ping`）。

### 3.2 `api-contract`（已本地验证）

两件事都在这一个 Job 里，都不依赖 Node：

- `check-api-contract.ps1`：预期 `unmatched: 0`，退出码 0；
- `check-frontend-consistency.ps1`：预期 `FRONTEND CONSISTENCY OK`，退出码 0（本地实测 `api 对象 15 个 / 后端 DTO record 43 个 / 视图 15 个 / 路由 14 个`）。

若报 `pwsh: command not found`：runner 镜像变更，改用 `shell: bash` + `tools/check-api-contract.sh`（契约校验有等价的 bash 版本；一致性脚本目前只有 PowerShell 版，需要时再补 bash 版）。

一致性脚本会抓三类 vue-tsc 抓不到、运行时才炸的问题：页面调用了不存在的 `xxxApi.method`、后端 DTO 字段与前端 interface 漂移（前端多出的字段恒为 `undefined`）、菜单项指向不存在的路由。

### 3.3 `mysql-migration`（**首次真跑，最可能红**）

- 预期：`MySqlMigrationSmokeTest` 1 个用例通过。
- 排查顺序：
  1. **Skipped 而不是通过** → `-Dmysql.test.url` 没传进去（系统属性名写错或被引号吞掉）；
  2. **连接失败** → service 未就绪。MySQL 8 首次初始化要 20~40 秒，`health-retries: 10` × 10s 一般够；若仍失败，把 `--health-retries` 提到 15；
  3. **迁移脚本报错** → 这才是本 Job 存在的意义：某条 DDL 在真 MySQL 上不成立（索引长度、`ADD COLUMN IF NOT EXISTS` 不支持、`NOT NULL` 无默认值）。按 [`doc/05_数据库迁移演练与回滚预案.md`](05_数据库迁移演练与回滚预案.md) 第 4 节规范修脚本（**已发布的脚本只读，修正一律新建版本**）；
  4. **断言「重复 migrate 执行 0 个」失败** → 有脚本未记录成功状态，查 `flyway_schema_history`。
- 本地复现（需 Docker）：`bash tools/check-mysql-migration.sh` 或 `pwsh tools/check-mysql-migration.ps1`。

### 3.4 `admin-web-build`（**首次真跑，次可能红**）

- 预期：`vue-tsc --noEmit && vite build` 通过。
- 已降低的风险：把 3 处 `Record<string, { text: string; type: string }>` 收紧为 `'primary' | 'success' | 'info' | 'warning' | 'danger'` 字面量联合类型——`el-tag` 的 `type` prop 不接受任意 `string`，`strict: true` 下会报 `TS2322`。
- 若红在类型上：`tsconfig.json` 的 `noUnusedLocals` 为 `false`，所以不会因为未使用变量报错；`strict: true` 下常见来源是「给组件 prop 传了过宽的类型」「`any` 隐式转换」「可选 prop 未处理 `undefined`」。
- 若红在依赖上：仓库暂无 `package-lock.json`，`npm install` 每次都解析最新 minor 版本。首次跑通后**立即提交 lockfile**，并把 `cache-dependency-path` 指向它，避免「昨天还绿、今天因为上游 patch 就红」。
- 本地复现（需 Node 18+）：`cd admin-web && npm install && npm run build`。

## 4. 首次「红」的判断流程

| 现象 | 归类 | 处理 |
| --- | --- | --- |
| Job 在 checkout / 环境准备阶段失败 | 环境 | 修 workflow（runner 镜像、CLI 缺失、service 就绪） |
| 仅 `mysql-migration`、`admin-web-build` 红，其余绿 | 首次暴露 | 按 3.3 / 3.4 排查，属本次引入的门禁价值所在 |
| `backend-test` 红且指向某业务断言 | 真缺陷 | 本地 `mvn test` 复现（本地已全绿，若 CI 红说明存在环境差异，优先查时区、文件编码、路径分隔符） |
| `api-contract` 红且报 UNMATCHED | 真缺陷 | 前端声明的路径在后端不存在，改前端或补接口 |

## 6. 本地静态验证结论（CI 首次跑的前置能做的都已做完）

本机环境：`git` 有，但**仓库根目录没有 `.git`**；`gh` / `node` / `npm` / `docker` 均缺失。因此四个 Job 无法在本地真跑，只能做静态核对。已核对项：

| 核对项 | 结果 |
| --- | --- |
| `ci.yml` 引用的 7 个文件（workflow、两个校验脚本、迁移脚本、`package.json`、`pom.xml`、`MySqlMigrationSmokeTest`） | 全部存在 |
| YAML 结构：TAB 缩进（YAML 禁止） | 无 |
| Job 数量与完整性 | 4 个（`backend-test` / `api-contract` / `mysql-migration` / `admin-web-build`），均有 `name` 与 `runs-on` |
| 服务容器 | 2 个（Redis 用于限流原子性、MySQL 8 用于迁移演练） |
| `continue-on-error` 实际配置 | 0 处（仅剩注释文字）；门禁全是阻断 |
| 文件编码与行尾 | 无 BOM、纯 LF（对 `ubuntu-latest` 无影响） |
| `admin-web` 锁文件 | **全无**（`package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` 都不存在） |
| 本地可复现的校验 | 契约 `107/24/12 unmatched 0`、一致性 `OK`、后端 `128 用例 0 失败` |

**唯一无法在本地消除的不稳定源**：`npm install` 没有 lockfile，每次都解析最新 minor 版本，上游发一个 patch 就可能让「昨天绿的构建今天红」。这一点只能等首次跑绿后提交 `package-lock.json`（见第 5 节第 1 条），本地没有 Node 无法生成。

## 7. 执行侧待办（需具备 Git 历史与 GitHub 仓库）

1. `git init` → 提交 → 关联远端 → push，触发首次 workflow；
2. 按第 4 节判断每个红灯的归类（环境 / 首次暴露 / 真缺陷）；
3. 跑绿后按第 5 节固化，并把 `admin-web/package-lock.json` 提交回来；
4. 在分支保护里把 `backend-test` 与 `api-contract` 设为 required check（`mysql-migration` 与 `admin-web-build` 视团队节奏而定，但至少在 `main` 上应是阻断）。
