# 数据库迁移演练与回滚预案

> 面向：部署 / 运维 / 后端值班
> 对应代码：`backend/src/main/resources/db/migration/`、`backend/src/test/java/com/exam/platform/MySqlMigrationSmokeTest.java`
> 相关告警：[`deploy/prometheus/exam-platform-rules.yml`](../deploy/prometheus/exam-platform-rules.yml)

## 1. 为什么单独有一份迁移预案

表结构变更走 Flyway 版本化脚本（`V1__baseline.sql` … `Vn__xxx.sql`），应用启动时自动执行。这件事带来一个容易被忽视的性质：

**迁移失败 = 应用启动失败。** Flyway 在脚本报错时会中断启动流程，不会「跳过继续」。也就是说，一条在预发没跑过的 `ALTER TABLE`，可以让整个服务在发布窗口内起不来——不是接口 500，而是进程反复重启。

日常测试跑的是 H2 的 MySQL 兼容模式，它「兼容」的只是**语法形状**，被抹掉的差异恰好是生产首次迁移最容易翻车的地方：

| 差异点 | H2 兼容模式 | 真实 MySQL 8 | 翻车表现 |
| --- | --- | --- | --- |
| 索引前缀长度 | 不校验 | 单列索引 ≤ 3072 字节（utf8mb4 下 VARCHAR 约 768 字符） | 建索引直接报错 |
| 字符集 / 排序规则 | 忽略 | 库级 `utf8mb4_0900_ai_ci` | 大小写唯一约束行为不同 |
| `DATETIME` 精度 | 忽略小数秒 | 默认 0 位精度，小数秒被截断 | 时间比较出现 1 秒级偏差 |
| `ALTER ADD COLUMN ... DEFAULT` | 全表重写（内存库，感觉不到） | 8.0 走 instant add，但 **`NOT NULL` 且无默认值** 会就地回填 | 大表长时间锁表 |
| `COMMENT` 与 `IF NOT EXISTS` | 支持度更宽松 | `ADD COLUMN IF NOT EXISTS` **不支持** | 脚本语法错误 |

结论：**迁移必须在真 MySQL 上预先跑过一遍。** 这不是「最好有」，是发布前的前置条件。

## 2. 演练怎么做

### 2.1 CI（每次 PR 自动跑）

`.github/workflows/ci.yml` 的 `MySQL 8 · flyway migrate` job：起 `mysql:8.0` service 容器 → 跑 `MySqlMigrationSmokeTest` → 断言

- 全部迁移脚本（当前 V1..V10）执行成功——期望的脚本数由 Flyway 实际解析结果得出，**不写死在测试里**；
- 重复执行 `migrate` 是无操作（多实例同时启动、回滚后重跑是常态）；
- 关键表与索引真实存在：`trade_recon_anomaly` 的处置字段与 `idx_trade_recon_anomaly_handle`、额度池三张表（`sys_org_quota` / `sys_org_quota_recharge` / `sys_org_quota_consume`）、以及 V10 的对账索引（`idx_entitlement_ledger_recon`、`idx_sys_org_quota_consume_created`）。

> 这里曾经踩过一个坑：断言写的是「`migrationsExecuted == 3`」。脚本增到 V4..V10 后，这个 job 在 CI 上必然失败；而它平时被 `assumeTrue` 跳过，所以一直没人发现——**演练其实长期在测三年前的快照**。教训是：这类「数量」断言必须从实际解析结果推导，否则新增迁移脚本时会悄悄让门禁失真。

### 2.2 本地（提交迁移脚本前自己先跑）

```bash
# Linux / macOS
bash tools/check-mysql-migration.sh

# Windows PowerShell
pwsh tools/check-mysql-migration.ps1
```

脚本用 Docker 起一台临时 MySQL 8（端口 `33061`），跑完整迁移 + 抽查表结构，随后销毁容器。没有 Docker 时**直接报错退出**，不做静默跳过——跳过会让人误以为演练过了。

### 2.3 预发（发布前最后一道）

预发库必须是 MySQL 8 且**结构是生产的最新快照**。只在空库上演练会漏掉「给已有数据的大表加列」这类问题的真实耗时。

```sql
-- 演练前后对比这张表，确认历史脚本没被改动、没有版本断档
SELECT installed_rank, version, description, script, checksum, success
  FROM flyway_schema_history ORDER BY installed_rank;
```

任何已执行过的脚本被修改（checksum 变化）都会让 Flyway 在启动时**直接失败**。历史脚本只读，不补不改。

## 3. 回滚预案

### 3.1 原则

1. **不依赖自动化 undo。** Flyway 社区版没有 undo（undo 属商业版），且 DDL 的「撤销」在数据层面往往不可逆（删掉的列不会自动长回数据）。所以回滚是**人工脚本 + 备份恢复**。
2. **先备份，再迁移。** 迁移前对受影响表做逻辑备份（`mysqldump --single-transaction`），文件与发布单一起归档。
3. **结构与数据分开看。** 只加列/加表/加索引 → 回滚通常只需逆操作，数据零损失；涉及删列、改类型、挪数据 → 必须按「停机 + 备份 + 双写/双读」处理，不做在线迁移。
4. **应用先回滚，还是脚本先回滚？** 迁移是「向后兼容」的设计前提：新脚本只加不删（加列、加表、加索引），旧版本应用忽略新列即可继续服务。**因此常规步骤是：应用回滚到上一版本（脚本不回滚）**，等新版本问题定位清楚再重新发布。只有当新脚本明确破环了旧版本（例如改了既有的列类型 / 加了 `NOT NULL` 无默认值列）才需要执行脚本回滚。

### 3.2 三种场景的处置

**场景 A：迁移脚本本身在预发就失败（最常见）**

- 现象：应用启动即退出，日志 `FlywayException: Migration V3__xxx failed`，退出码非 0。
- 处置：**不发布**。修正脚本内容后重新演练。若该脚本已在某个环境（非生产）成功执行过，则**新建 `V4__fix`** 而不是改 V3（checksum 会拦）。

**场景 B：迁移成功，但新版本应用有故障**

- 处置：应用回滚到上一版本，脚本保留。旧版本应用对新列/新表无感，服务立即恢复。
- 例外：若新版本已写入数据到只有新版本认识的结构（例如对账处置状态），回滚应用会「看不到但数据仍在」，属可接受状态，等修复后再上。

**场景 C：迁移成功，但数据被写坏 / 必须撤回结构变更**

- 处置顺序：
  1. 摘流量 / 停写（确认无正在进行的事务）；
  2. `mysqldump` 受影响表；
  3. 执行本文 `3.3` 的逆操作脚本；
  4. 回滚应用版本；
  5. 用备份校验行数（`SELECT COUNT(*)`）与关键业务字段。

### 3.3 逆操作脚本（按版本登记）

逆操作脚本放在 `deploy/rollback/`，命名与迁移脚本一一对应，**只在场景 C 使用**，日常发布不执行。

```sql
-- deploy/rollback/V3__recon_anomaly_handling.down.sql
-- 撤回对账异常处置字段。执行前必须先停写并备份 trade_recon_anomaly：
--   mysqldump --single-transaction exam_platform trade_recon_anomaly > trade_recon_anomaly.bak.sql
DROP INDEX idx_trade_recon_anomaly_handle ON trade_recon_anomaly;
ALTER TABLE trade_recon_anomaly
  DROP COLUMN handled_at,
  DROP COLUMN handled_by,
  DROP COLUMN handle_remark,
  DROP COLUMN handle_status;
-- 注意：此操作会永久丢失所有处置记录（谁处理了哪条异常、为什么不修）。
-- 若处置记录仍有用，先导出：SELECT * FROM trade_recon_anomaly WHERE handle_status <> 'PENDING';
```

> 逆操作里**不要**顺手 `DELETE FROM flyway_schema_history`，除非确实要让该版本重新执行；删错一行会让后续所有迁移的判断错位。

### 3.4 停机窗口检查清单

发布涉及「大表结构变更」时按此顺序执行，每步都要有对应的回退动作：

1. 备份受影响表（`mysqldump --single-transaction`），记录文件大小与 `COUNT(*)`；
2. 关停定时任务（对账、消息重试、超时收卷），避免迁移期间写入；
3. 发布新版本（Flyway 自动迁移）→ 检查启动日志 `Successfully applied N migrations`；
4. 验证：`/api/actuator/health` 为 `UP`、登录、下单、答题保存各一次冒烟；
5. 逐步放量；观察 5xx 比例、答题保存 p99、连接池排队（见告警规则）；
6. 恢复定时任务；
7. 归档备份文件与发布单。

## 4. 新增迁移脚本的规范

- **只加不删**：新脚本只允许「加表 / 加列 / 加索引 / 放宽约束」，删改既有结构必须单独走变更评审 + 本文预案。
- **文件只读**：已发布的脚本不得修改，修正一律新建版本。
- **默认值必须显式**：`NOT NULL` 列一定带 `DEFAULT`，否则 MySQL 会对已有行就地回填，大表上会长时间占用。
- **索引前缀**：`VARCHAR` 建单列索引时长度 ≤ 768（utf8mb4），超长改用前缀索引 `(col(255))`。
- **幂等性**：脚本自身不必幂等（Flyway 保证只跑一次），但**重复执行 migrate 必须无副作用**——这条由 `MySqlMigrationSmokeTest` 每次都验。
- **配套逆操作**：涉及删改的脚本，必须在 `deploy/rollback/` 提交同名 `.down.sql`，否则变更评审不通过。
