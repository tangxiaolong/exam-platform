# 10 · 会员订阅 / 优惠券 / SKU 与部分退款

> 对应 Step 5 第一组。代码：`modules/trade/`（`CouponService`、`RefundService`、`TradeService`），
> 迁移：`V11__mall_sku_coupon_item.sql`。

## 一、为什么这三件事必须一起做

| 缺谁 | 会怎样 |
| --- | --- |
| 缺 SKU | 商品只有一个价，券无法按商品限定、订单金额没有真实来源 |
| 缺订单明细 | 部分退款算不出「退哪一项、退多少」，权益也无从归因 |
| 缺优惠券 | 谈不上营销，会员与课程的组合定价只能靠改价硬编码 |

## 二、数据模型

```text
mall_sku                 商品下的销售单元（月卡/季卡/年卡），价格与时长落在 SKU 上
trade_order_item         订单明细：名称与单价是下单快照，refunded_amount_fen 记录已退累计
marketing_coupon         券模板：满减 / 折扣、门槛、发行量、人均限领、适用范围
marketing_coupon_grant   持券记录：UNUSED → LOCKED → USED
trade_order              + coupon_grant_id + item_count
trade_refund             + order_item_id + quantity（部分退款）
```

四个决定：

1. **明细落快照**：改价/改名不影响历史订单与退款金额；
2. **优惠只记订单级**：分摊到明细会引入尾差，还要回答「退款时谁承担折扣」；
3. **默认 SKU 必须存在**：迁移回填 + 运行期 self-healing + 新建商品自动创建，三条兜底；
4. **券必须有 LOCKED**：下单锁、支付成功核销、关单回滚。

## 三、券的生命周期

```text
claim ──► UNUSED ──下单──► LOCKED ──支付成功──► USED
                              └──订单关闭/超时──► UNUSED
```

- **领取控量靠一条原子 UPDATE**：`UPDATE marketing_coupon SET claimed_quantity = claimed_quantity + 1
  WHERE total_quantity = 0 OR claimed_quantity < total_quantity`。先 count 再 insert 在并发下必然超发。
- **人均限领**由业务校验 + 唯一约束双重保证。
- **回滚时保留 order_id**：便于追溯「这张券曾被哪笔订单占用过」。

## 四、抵扣算法与三条边界

| 类型 | 计算 |
| --- | --- |
| 满减 `AMOUNT` | `discount = min(valueFen, amountFen)` |
| 折扣 `DISCOUNT` | `discount = amountFen × (100 - percent) / 100`，向下取整，再 `min(maxDiscountFen)` |

三条边界（都对应真实事故类型）：

1. **门槛按优惠前金额判定**：`amountFen >= thresholdFen`；
2. **抵扣后实付必须 ≥ 1 分**：微信不收 0 元单，且 0 元订单会让退款与对账失去基准；
3. **折扣券建议配封顶**：不封顶时订单金额越大抵扣越多，是最容易被薅的口子。

## 五、部分退款金额规则

```text
明细实付 = 明细原价 × 订单实付 ÷ 订单原价          （优惠按整单比例摊到每一行）
每件实付 = 明细实付 ÷ 明细数量                    （与「已退多少」无关）
本次退款 = 每件实付 × 本次数量                      （受「明细实付 - 已退累计」封顶）
```

**必须是这个顺序**。开发过程中真实踩到的两个 bug：

1. **每件实付用了「剩余可退 ÷ 数量」**：退 2 件里的第 1 件算 9400，第 2 件只剩 4700，
   累计永远退不到实付。测试断言 `expected 9400 but was 4700` 才暴露。
2. **默认 SKU 缺失**：V11 迁移给存量商品回填了 SKU，但演示数据在迁移**之后**插入，
   下单时找不到规格 → 整条链路 500。修复是让 `resolveSku` 就地创建默认 SKU 并处理并发唯一索引冲突。

## 六、权益回收策略（需要运营知晓）

| 场景 | 权益处理 |
| --- | --- |
| 整单退完（累计退款 ≥ 实付） | 回收未使用部分（`revokeByOrder`），账户置 `REVOKED` |
| 部分退款 | **不回收**，账户保持可用 |

部分退款不回收是有意的：权益是「次数包」语义，按比例回收会引出「退掉的是哪几份、
已用完的算不算」的争议，而这类争议最终都靠人工裁决。与其算一个可能错的数，
不如保持账户不动并留下审计记录。若业务确实需要按比例回收，应作为独立需求评估。

## 七、会员续费顺延

`EntitlementService.grant` 对 `MEMBER` 类型改为**叠加时长**：

```text
新到期日 = max(今天, 旧到期日) + 本次时长
```

只对 `MEMBER` 生效，其余权益类型保持「以最新到期日为准」，避免动到额度类既有行为。

## 八、接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/products/{id}/skus` | 在售规格 |
| POST | `/v1/orders` | 入参新增 `skuId`、`couponGrantId`（可空） |
| GET | `/v1/orders/{id}/items` | 订单明细 |
| GET | `/v1/coupons/claimable` | 可领券（已领完/超人均不返回） |
| POST | `/v1/coupons/{code}/claim` | 领券 |
| GET | `/v1/coupons/mine?status=` | 我的券 |
| POST | `/v1/orders/{id}/refunds` | 退款；不传 `orderItemId` 为整单，传则为部分退款 |
| POST | `/v1/admin/refunds/{id}/approve` | 审核通过（既有接口） |

## 九、测试覆盖

`TradeCouponFlowTest`（4 个用例）：

- 领券人均限领 + 领完从可领列表消失；
- 用券下单：金额由服务端算、下单只锁定、支付成功才核销；
- 门槛不足 / 抵扣后 0 元均被拒；
- 部分退款按实付折算、累计达实付后转 `REFUNDED` 并回收权益、已全退再申请报 `REFUND_NOTHING`。

## 十、已知限制

1. **管理端没有券的 CRUD**：目前建券只能写 SQL，运营无法自助；
2. **小程序未接 SKU 选择与券选择**：接口已就绪，页面仍是「点商品直接下单」；
3. 券模板不支持「限定时段可用」「指定用户群发放」，需要再做；
4. 部分退款确需回收权益时没有入口，只能人工调整账户。
