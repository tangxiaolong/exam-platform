# 08 · 小程序离线答题与断网重连验证清单

> 用途：`miniprogram/utils/answer-queue.js` 与 `pages/exam/taking.js` 的离线答题能力，
> 逻辑已由代码与后端测试覆盖，但「断网→恢复→补交」这条链路必须在真机或微信开发者工具里
> 实际点一遍才算验过。本清单是执行脚本，逐条勾选即可。
>
> 相关实现：`answer-queue.js`（本地队列）、`taking.js`（入队 / 重放 / 交卷前补交）。

## 〇、自动化与人工的分界

| 层 | 覆盖者 | 命令 |
|---|---|---|
| 队列语义（去重 / 上限 / 隔离 / 出队 / 冲突） | `tools/miniprogram-tests/answer-queue.test.js`（12 个用例） | `node --test tools/miniprogram-tests/` |
| 后端答案保存 / 交卷幂等 / 版本冲突 | `AttemptAnswerTest`、`AttemptSubmitIdempotencyTest` 等 | `cd backend && mvn test` |
| 网络事件触发、toast 可见性、页面状态渲染 | **只能真机 / 开发者工具** | 本清单第二～三节 |

下表中「自动」= 已有自动化用例，真机复验只用于确认体验；「真机」= 必须在设备上点。
**真机最小执行集**：MP-01、MP-02、MP-05 三条（其余各条的核心判定已被自动化覆盖，若时间紧可跳过，记为「自动化已验证」）。

### 本清单对应的实现修复（静态核对发现，共 4 处）

以下问题在写自动化用例的过程中暴露，均已修复——它们都属于「答案丢失」而不是「提示不准」：

| 位置 | 缺陷 | 后果 |
|---|---|---|
| `answer-queue.flush` | `catch` 不区分错误类型，业务错误（如已交卷）也被当作「还在断网」 | 该条永不成功却永不丢弃，每次 `onShow` 重试一次，并把它后面本来能同步的答案一起卡住（对应 MP-10） |
| `taking.scheduleSave` | 每次作答都 `clearTimeout` 上一个定时器、只记最后一个题号 | 400ms 内连续作答几道不同的题时，前面几题的保存被静默取消，只在内存里，交卷也不会带上 |
| `taking.confirmSubmit` | 交卷前只补交离线队列，不冲刷内存中防抖窗口内的答案 | 点完最后一题立刻交卷（<400ms），该题不进服务端 |
| `taking.confirmSubmit` | `wx.hideLoading()` 只在「队列仍有剩余」时调用 | 同步成功直接交卷时 loading 遮罩残留，页面看起来卡死 |

修复后的交卷顺序固定为：**清防抖定时器 → 冲刷内存待保存答案 → 重放离线队列 → 仍有剩余则明确阻止交卷并提示**。四条阻断项（MP-02/04/05/08）的判定因此从「依赖点击时序」变成「顺序固定、可单测」。

## 二、用例清单

### MP-01 断网时答题 → 入队并明确提示（队列：自动；toast 与顶部计数：真机）

1. 进入答题页，切到**离线**。
2. 选择一道题并点选答案。

| 预期 | 说明 |
|---|---|
| 出现 toast「网络异常，答案已暂存本地」 | 只在队列首次有内容时提示一次，不每条都弹 |
| 页面顶部「待同步 N」变为 1 | `pendingCount` 来自队列真实长度 |
| 本地存储出现 `exam_answer_queue` | 开发者工具 → Storage 面板可直接查看 |

### MP-02 恢复网络 → 自动重放并清空队列（队列：自动；网络事件触发：真机）

1. 保持上一状态（队列里有 1~3 条）。
2. 切回**在线**。

| 预期 | 说明 |
|---|---|
| 无需手动操作，队列自动开始重放 | 由 `wx.onNetworkStatusChange` 触发 |
| 出现 toast「离线答案已全部同步」 | 仅在「之前有、现在清零」时提示 |
| 「待同步」归零、「已保存」数增加 | 两者都来自真实状态 |
| 后端日志出现对应次数的 `PUT .../answers/...` | 确认不是前端自己把队列清空了事 |

### MP-03 切后台再回来 → 补交（队列持久化：自动；`onShow` 触发：真机）

1. 离线答题产生 1 条队列。
2. 保持离线，把小程序切到后台，再切回前台（或杀掉小程序后从「最近使用」重进同一考试）。

| 预期 | 说明 |
|---|---|
| 页面 `onShow` 触发一次重放尝试 | 网络仍断时静默失败、队列保留 |
| 恢复网络后仍能全部同步 | 队列存在 `wx.setStorageSync`，杀进程也不丢 |

### MP-04 同一道题多次作答 → 只重放最后一次（自动）

1. 离线状态下对**同一题**改选 3 次（A → B → C）。

| 预期 | 说明 |
|---|---|
| 「待同步」始终为 1 | 队列按 `scope+targetId+questionId` 去重 |
| 恢复网络后服务端最终答案是 C | 重放的是「最后想选的」，不是每次点击 |

### MP-05 交卷前自动补交（自动覆盖顺序；loading 文案与阻止交卷的提示：真机）

1. 离线答题产生至少 1 条队列，**保持离线**。
2. 点击「交卷」。

| 预期 | 说明 |
|---|---|
| 先出现 loading「正在同步离线答案」 | 交卷前强制冲刷内存待保存答案 + 重放离线队列 |
| 同步不完时**不继续交卷**，弹窗告知仍有 N 条未同步 | 不能把断网前那一版当最终答案提交 |
| 恢复网络后再点交卷 → 先同步再提交 | 顺序固定：清定时器 → 冲内存 → 冲队列 → 交卷 |
| 同步成功直接交卷时 loading 会消失 | 不能留下遮罩让页面看起来卡死 |

### MP-06 版本冲突 → 让用户知道被覆盖（队列侧：自动；页面回显：真机）

1. 两个端（如小程序 + 后台/另一设备）同时对同一题作答，制造服务端版本更新。
2. 小程序端提交后服务端返回 `saved=false`。

| 预期 | 说明 |
|---|---|
| 页面出现冲突提示（非静默） | `onAnswerConflict` 必须可见，否则用户以为是自己的答案 |
| 「待同步」不残留该条 | 该条已成功送达，只是被服务端更新版覆盖 |

### MP-07 交卷幂等：重复点击 / 弱网重试不产生两次交卷（后端：自动；连点体验：真机）

1. 快速连点「交卷」两次（或弱网下反复点）。

| 预期 | 说明 |
|---|---|
| 只出现一次交卷结果，不报「已交卷」错误 | `requestId = mp-submit-{attemptId}` 固定，后端按幂等处理 |
| 后端只有一条 SUBMITTED 记录 | 与后端 `AttemptSubmitIdempotency` 用例一致 |

### MP-08 交卷成功后队列清空 → 下一场不串题（自动）

1. 正常交卷成功。
2. 进入下一场考试。

| 预期 | 说明 |
|---|---|
| 交卷成功后该场次队列被 `clear` | 避免把上一场答案重放进下一场 |
| 下一场「待同步」为 0 | 若不为 0，即为串场风险，按阻断缺陷处理 |

### MP-09 队列上限（自动）

1. 在 Storage 里手动往 `exam_answer_queue` 塞 200+ 条。
2. 再作答一题。

| 预期 | 说明 |
|---|---|
| 队列保持 200 条上限，不无限增长 | 正常一场考试几百题，200 条足够；上限是防写爆本地存储的兜底 |

### MP-10 业务错误不入队（入队判断：代码静态；出队与不阻塞：自动；真实业务错误：真机）

1. 离线提交后，让该场考试在**另一处**被交卷/超时关闭，再恢复网络。

| 预期 | 说明 |
|---|---|
| 带业务 `code` 的失败**不**入队 | 只有网络类失败才暂存，避免把注定失败的请求永远重试 |
| 已在队列里的条目重放时遇到业务错误 → 出队并继续下一条 | 否则它会每次 `onShow` 重试一次，并挡住后面能成功的答案 |

## 四、与自动化测试的边界

| 层 | 谁覆盖 | 说明 |
|---|---|---|
| 后端答案保存 / 交卷幂等 / 版本冲突 | `AttemptAnswerTest`、`AttemptSubmitIdempotencyTest` 等（`mvn test` 全绿） | 服务端行为已自证，不需要在真机重复验 |
| 队列语义（去重 / 上限 / 隔离 / 出队 / 冲突） | `tools/miniprogram-tests/answer-queue.test.js`（`node --test`） | 用最小 `wx` 桩在 Node 里跑，CI 的 `miniprogram-test` Job 每次都跑 |
| 网络事件触发 / toast 可见性 / 渲染 | 只能真机 | `wx.onNetworkStatusChange` 在模拟器的行为与真机不完全一致 |
| 交卷前冲刷顺序 | 代码结构固定（清定时器 → 冲内存 → 冲队列 → 交卷），由代码评审保证 | 页面层依赖 `Page()` 与 `wx`，未做端到端桩 |

## 五、已知限制

1. 队列只按「场次」隔离，不支持同一场考试在**两个设备**同时离线答题——最后同步的一方会看到冲突提示，这是预期行为；
2. 本地存储写失败时只提示「答案可能未保存」，不做重试；此时应引导用户检查存储空间；
3. 清单里的 MP-09 需要手工改 Storage，属于非常规路径，验证后可清理本地数据；
4. 队列在 `flush` 中遇到业务错误会**直接丢弃该条**——答案注定无法保存（场次已关闭/已交卷），保留只会反复失败并阻塞后续条目。这是有意的取舍，不是遗漏。
