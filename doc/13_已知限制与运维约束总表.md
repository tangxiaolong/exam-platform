# 13 · 已知限制与运维约束总表

> 这份表取代散落在各文档末尾的「已知限制」清单。
>
> **为什么集中**：各文档的限制段落格式不一，有的写了原因、有的只写现象，且都缺「何时该补」。
> 更麻烦的是它们会随代码演进而失真——`doc/12` 曾同时记载「没有知识点 CRUD」「难度配比未实现」，
> 两条都已不成立，因为写的是**当时的计划**而不是**当时的事实**。
>
> **收录规则**：每条必须能填满四列，且末尾给出**可核实的文件与行号**。
> 写不出行号的，只能标「未核实」，不许写成事实——本表先后出现过 7 处失真，全部源于「凭印象写」。

## 二、不是限制，别误当成待办

有几处文档里写着像缺口、实际是**有意设计**：

| 项 | 为什么不是缺口 |
|---|---|
| 平台证书只缓存进程内、多实例各一份 | 证书是幂等的公共数据，共享缓存带来的复杂度远大于省下的几次 HTTP 请求 |
| 小程序队列 `flush` 遇业务错误直接丢弃该条 | 场次已关闭/已交卷时，保留只会反复失败并阻塞后续条目 |
| 未标注知识点的题目不被知识点抽中 | 把 NULL 当通配会让「覆盖度」失真，而覆盖度是这个功能唯一的意义 |
| 公告未发布/已过期一律返回「不存在」 | 区分「不存在」与「不可见」等于提供存在性探测 |
| 部分退款不回收权益 | 权益是次数包，按比例回收要先回答「退掉的是哪几份」，争议成本大于收益 |

## 三、核对中发现的失真类型

| 类型 | 例子 | 危害 |
|---|---|---|
| **文档说没有、代码其实有** | 「没有知识点管理端 CRUD」（`ContentAdminController` 一直有）、「难度配比未实现」 | 做重复工作，实际发生过一轮返工 |
| **文档说未做、其实已做** | 「角色软删未提供接口」、「JWT 无黑名单」（角色权限早已每请求现查） | 低估现状，重复劳动 |
| **把有意取舍记成缺失** | 「部分退款回收权益没有入口」 | **最危险**：照着做会去实现一个本该被拒绝的方案 |
| **把已改善记成未做** | 「错题本题目被删时静默跳过」 | 低估现状 |

根因相同：**文档记录的是「当时的计划」，而不是「当时的事实」**。越新的文档越容易错，因为它离计划最近、离验证最远。

## 四、维护约定

1. 新增限制先进本表，不在别处另起清单；
2. 每条必须四列齐；缺「何时必须补」的条目等于没有决策；
3. 限制被解决后，保留一行记录并标注结论——**删掉会让人重复踩坑**；
4. 每轮功能交付时顺手检查本表，与本轮改动相关的行要么更新、要么确认仍然成立；
5. **每条必须带文件与行号**。写不出行号的先标「未核实」，不许写成事实。
   本表先后 7 处失真全部是「凭印象写」造成的，而严格核过行号的 8 条**没有一条出错**；
6. 新增限制时先问一句：这到底是「我们没做」，还是「我们决定不做」？后者应进第二节，不进第一节。
